# ARCHITECTURE — How the machine works

> The most important section is **"Generated vs hand-written"**. Editing a generated
> file by hand is the #1 mistake an agent can make in this repo.

## Generated vs hand-written files

| File / dir | Status | Regenerated by | To change it, edit… |
|---|---|---|---|
| `packages/icons/src/icons/*.ts` (components) | 🤖 **GENERATED** (committed) | `scripts/generate-icons.mjs` | the generator or `scripts/animations.mjs`, then regenerate |
| `packages/icons/src/icons/*.spec.ts` | 🤖 GENERATED (committed) | `scripts/generate-icons.mjs` | the generator's test template |
| `packages/icons/src/icons/index.ts` (barrel) | 🤖 GENERATED | `scripts/icon-catalog-writer.mjs` (via generate/sync) | nothing — always re-run `pnpm run sync:icons` |
| `src/app/data/icon-catalog.ts` | 🤖 GENERATED | `scripts/icon-catalog-writer.mjs` (via generate/sync) | nothing — re-run sync |
| `packages/icons/dist/**` | 🤖 build output, not committed | `scripts/build-lib.mjs` | build config (`ng-package.json`, the script) |
| `packages/icons/src/lib/icon-base.ts` | ✍️ hand-written | — | directly (this is the shared API — see breaking-change policy) |
| `packages/icons/src/types/icon.types.ts` | ✍️ hand-written | — | directly (public types) |
| `src/app/data/icon-metadata.ts` | ✍️ hand-curated, machine-reformatted | `scripts/icon-catalog-writer.mjs` | edit entries directly; the writer preserves them and infers missing ones |
| `scripts/*.mjs` | ✍️ hand-written | — | directly |
| everything in `src/app/` except `data/icon-catalog.ts` | ✍️ hand-written | — | directly |

**Caveat on custom icons:** ~38 icons have no Heroicons source. The generator *extracts their current SVG paths from the committed component* and re-emits them. So their SVG content effectively lives in the committed file — but structure/animation/styles still come from the generator. To change a custom icon's *drawing*, you may edit its paths in place and regenerate; to change anything else, go through the generator.

## Pipeline 1 — Icon generation

```
node_modules/heroicons/24/outline/*.svg   (outline paths)
node_modules/heroicons/24/solid/*.svg     (filled paths)
existing committed custom icons           (extracted paths)
        │
        ▼
scripts/generate-icons.mjs
  ├─ normalizes SVGs (strip sizes, force currentColor)
  ├─ resolves each icon's animation → scripts/animations.mjs
  │    ICON_ANIMATIONS  (explicit name → recipe map)
  │    FALLBACK_ANIMATIONS (pattern → recipe, first match wins)
  │    RECIPES (~70 builders: keyframes + optional pathLength/pathClasses)
  ├─ emits packages/icons/src/icons/<name>.ts   (component, scoped @keyframes)
  ├─ emits packages/icons/src/icons/<name>.spec.ts
  └─ updates barrel + website catalog + metadata (via scripts/icon-catalog-writer.mjs)
```

- Run with `pnpm run generate:icons` (add `--overwrite` to force-regenerate all).
- A recipe returns: `keyframes` (scoped as `lmn-<icon-name>`), optional `pathLength: true` (enables stroke-draw via `pathLength="1"`), optional `pathClasses` (`.lmn-path-1`… for staggered multi-part motion), `base` and `animate` CSS blocks.
- Every generated component embeds the shared `prefers-reduced-motion` block.

## Pipeline 2 — Catalog sync

`pnpm run sync:icons` (`scripts/sync-icons.mjs`) scans `packages/icons/src/icons/*.ts`, extracts each class name via regex, and rewrites — through the shared writers in `scripts/icon-catalog-writer.mjs`, also used by `generate-icons.mjs` (single source of truth for these templates):
- `packages/icons/src/icons/index.ts` — the barrel.
- `src/app/data/icon-catalog.ts` — imports every icon via its `lumen-icons/<name>` subpath and exports the catalog array the website renders, with category/aliases inlined from the metadata.
- `src/app/data/icon-metadata.ts` — existing entries are preserved verbatim; icons missing one get an inferred category + aliases.

The website reads category/aliases straight from the catalog. **Review inferred metadata for new icons** — inference is name-pattern based, so hand-tune category/aliases in `icon-metadata.ts` when the guess is wrong.

## Pipeline 3 — Library build & publish

```
pnpm run build:lib  →  scripts/build-lib.mjs
  ├─ ng-packagr (packages/icons/ng-package.json) → APF output in packages/icons/dist/
  │    (FESM2022, Ivy partial compilation, unified .d.ts)
  └─ post-build: generates per-icon re-export stubs + final package.json#exports map
       so `lumen-icons/<name>` and `lumen-icons/icons/<name>` resolve for consumers

pnpm run check:package  →  build:lib + publint (validates the exports map)
pnpm run publish:icons  →  scripts/publish-icons.mjs (runs checks, then npm publish; --dry-run available)
```

`scripts/rebuild-legacy-icons.mjs` is a one-off migration helper — ignore unless a task explicitly involves it.

## Library runtime design

- `LmnIconBase` (`packages/icons/src/lib/icon-base.ts`) is an **abstract `@Directive`** holding all 12 inputs, computed host styles (color/tone resolution, background soft/solid via `color-mix`, padding, radius), and ARIA host bindings. Icon components `extend` it and contribute only: selector, scoped styles (keyframes), and the SVG template with an `@if` switch between outline and filled variants.
- Tones resolve to CSS custom properties (`var(--primary, currentColor)` etc.) — the library defines **no** values for these variables; consumers' themes do. Fallback is always `currentColor`.
- Public API surface = `packages/icons/src/index.ts` → re-exports `types/icon.types` + the icon barrel. `LmnIconProps` / `LmnIconInstance` in `icon.types.ts` are the public contract — changes there follow the breaking-change policy.

## App structure (`src/`)

- AnalogJS file-based routing: `src/app/pages/index.page.ts`, `icons.page.ts` (+ `icons.page.html`), `docs.page.ts`. Default exports are the page components. SSR disabled (`static: true`).
- Path alias `lumen-icons → packages/icons/src/index.ts` in root `tsconfig.json` — the app consumes **library source** directly in dev; no build step needed. Vite config also maps the per-icon subpaths.
- Shared app pieces: `components/` (icon-card, theme-toggle), `services/` (clipboard, theme), `types/icon-entry.type.ts`.
- App UI chrome uses `@voltui/components` (volt-button, volt-card, volt-tabs, …) — see CLAUDE.md's volt-ui table for available selectors.

## TypeScript configs

- Root `tsconfig.json`: strict base + the `lumen-icons` path alias. Never relax strictness flags.
- `tsconfig.app.json`: the app (includes `*.page.ts`).
- `packages/icons/tsconfig.lib.json`: the library (excludes specs).
- `pnpm run typecheck` runs both; a change can pass one and fail the other — always run both.
